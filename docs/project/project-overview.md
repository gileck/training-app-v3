# Training App — Project Overview

## Purpose

A personal strength-training tracker (mobile-first PWA). A user defines **training plans** — a named program of N weeks (1–52) containing a list of exercises, each with weekly targets (sets × reps, weight, or duration for static holds). During the week the user **logs completed sets** per exercise; progress resets each week of the plan. Exercises can be grouped into named **workouts** ("Push Day") for session-oriented training, and a live **Active Workout** mode runs a session with rest timers, supersets, and an AI-generated warmup.

Plans can be created manually, **generated by AI from pasted free text** (e.g. a program from a coach or article), **exported/imported as JSON**, or **shared via public link** — the recipient sees a preview and can add the plan to their own account.

It is a standard multi-user app (each user sees only their own data; signups are admin-approved per the template default), but in practice a single-owner personal app. An in-app AI agent, **Coach**, can read and modify the user's training data through tools.

A key implementation choice with business impact: plan exercises and weekly progress are **local-first** — the client store (localStorage) is the source of truth, synced to the server in the background with explicit conflict resolution when another device/agent wrote to the same plan.

## Routes

### `/` — Home (week view)

**What it does:** The daily-use screen. Shows the active plan's exercises for the currently selected week and lets the user log sets. Implemented in `src/client/routes/project/Home/`.

**UI / UX:**
- Week navigator (prev/next, capped at 1..durationWeeks) with a week progress bar (completed/total sets, skipped exercises excluded)
- Two tabs: **Exercises** (flat list, grid/list toggle, grouped into incomplete / completed / skipped) and **Workouts** (collapsible cards per saved workout with per-workout set allocation)
- Tap +/− on an exercise card to log/remove a set; "complete all" finishes remaining sets; undo via toast
- Selection mode (tap cards) → action bar: Start Workout / Edit / Skip / View details
- An exercise is "done" when logged sets ≥ target sets; sets logged without an explicit workout are auto-allocated to the first workout with remaining capacity

**APIs:**
| Endpoint | What it does |
|---|---|
| `training-plans/list` | plans + which is active (`src/apis/project/training-plans/handlers/listPlans.ts`) |
| `plan-data/sync` / `plan-data/version` | background local-first sync of exercises + skip flags; version check detects external writes (`src/apis/project/plan-data/handlers/`) |
| `activity-logs/add-activity`, `delete-activity` | each set tap creates/removes a `setLogs` document |
| `plan-workouts/list` | saved workouts for the Workouts tab |

**Data:** `setLogs` (one doc per completed set: planExerciseId, weekNumber, setNumber, completedAt, optional workoutId — the **source of truth for progress**), `planExercises`, `exerciseProgress` (only `isSkipped` is live; setsCompleted/isDone are legacy).

### `/training-plans` — Training Plans

**What it does:** Manage the plan library: create, edit, activate, duplicate, export, import, share, delete. Implemented in `src/client/routes/project/TrainingPlans/`.

**UI / UX:**
- Plan cards (active plan first, badge) with action menu: Set Active / Edit / Duplicate / Export / Share / Delete (confirm dialog)
- **Create with AI** dialog: paste free-form program text → AI generates a draft → preview with per-exercise match status against the library → user resolves unmatched exercises → commit
- Export dialog (JSON file or clipboard), Import dialog (paste/file → preview → commit)
- Share dialog generates `/share/{token}` — token is just base64url of `{u: userId, p: planId}` built client-side (`components/SharePlanDialog.tsx`); no expiry/revocation
- Tapping a card opens the nested ManagePlan editor

**APIs:**
| Endpoint | What it does |
|---|---|
| `training-plans/create` | new empty plan; **first plan is auto-activated**; durationWeeks 1–52 |
| `training-plans/set-active` | activates one plan, deactivates all others (single active plan rule) |
| `training-plans/delete` | **cascades**: setLogs → weeklyProgress → exerciseProgress → planExercises → plan (`handlers/deletePlan.ts`) |
| `training-plans/duplicate` | copy with " (Copy)" suffix, inactive, creationSource='duplicate' |
| `training-plans/generate-from-text` | AI (`AIModelAdapter`, JSON output) builds a draft plan; exercises matched to the library by exact/normalized name with suggestions for unresolved; preview only, returns cost (`handlers/generatePlanFromText.ts`) |
| `training-plans/create-from-text` | commits a draft: plan + custom exercise definitions for unresolved (when autoResolve) + planExercises + planWorkouts; limits: 200 exercises, 50 workouts; best-effort cleanup on partial failure (`handlers/createPlanFromText.ts`) |
| `training-plans/export` / `match-imported` | versioned JSON export ("1.0", includes exerciseDefIds for exact re-import matching); import validates + matches by id-then-name into a draft preview |

**Data:** `trainingPlans` (name, durationWeeks, isActive, creationSource: manual\|ai\|import\|share\|duplicate, lastDataSyncedAt).

### `/training-plans/:planId` — Manage Plan (editor)

**What it does:** Edit a plan's exercises and workouts. Implemented in `src/client/routes/project/ManagePlan/`.

**UI / UX:**
- **Exercises tab:** browse/search the exercise library (system + own custom, muscle-group filters), add (single or multi-select bulk), configure sets/reps/weight/duration/comments, reorder, delete, and per-plan **overrides** (rename, replace image, etc. without touching the base definition)
- **Workouts tab:** create/edit named workouts as ordered subsets of plan exercises, with optional per-workout sets override; reorder/delete
- Local-first: edits hit the Zustand store instantly and sync to the server debounced (~1s); a **sync-conflict dialog** appears when the server copy is newer than the local one (edited from another device or by the Coach agent) — user picks "take server" or "force mine"

**APIs:**
| Endpoint | What it does |
|---|---|
| `plan-data/sync` | bulk upsert exercises + skip flags with conflict detection vs `lastDataSyncedAt`; deletes exercises missing from the payload (`handlers/syncPlanData.ts`) |
| `plan-exercises/*` (list/add/bulk-add/update/delete/reorder) | CRUD; delete **cascades to that exercise's setLogs + exerciseProgress**; add validates sets ≥1, reps ≥1, library access |
| `plan-exercises/upload-override-image` | base64 → Vercel Blob upload, URL written into overrides (kept out of the offline sync payload) |
| `plan-workouts/*` (list/create/update/delete/reorder) | workout CRUD; items validated to belong to the plan; tolerant of optimistic temp IDs |
| `exercise-definitions/*` | library: create/update/delete custom exercises (with Blob image upload); **delete is blocked if the exercise is used in any plan**; system exercises are read-only |

**Data:** `planExercises` (targets + order + sparse `overrides`), `planWorkouts` (items: planExerciseId, order, sets?), `exerciseDefinitions` (name, image, primary/secondary muscles, type, isBodyweight, isStatic, isSystem vs per-user custom).

### `/active-workout` — Active Workout (live session)

**What it does:** Runs a live training session over a chosen set of exercises (ad-hoc selection or a saved workout). Implemented in `src/client/routes/project/ActiveWorkout/`; session state in `src/client/features/project/workout/` survives page refresh.

**UI / UX:**
- Current-exercise card with +1 set logging; session progress (X/Y sets) shown in the **top nav status bar** app-wide while active
- Configurable rest timer (5–999s, optional auto-start after each set, audio cue, "rest complete" banner)
- **Superset mode:** pair two exercises and alternate with a shared rest timer
- All-exercises overlay to jump around; add exercises mid-session; end-early confirmation
- **Save workout** — name the session and persist it as a reusable plan workout
- **AI warmup generator:** sends the session's exercises (muscles, sets/reps/weight) to the AI and renders a 5–10 min markdown warmup routine, showing the AI cost (`src/apis/project/workout-warmup/server.ts`)

**APIs:** `activity-logs/add-activity` (set logging), `plan-workouts/create` (save as template), `workout-warmup/generate` (AI warmup).

**Data:** writes `setLogs` (tagged with `workoutId` when launched from a saved workout).

### `/progress` — Progress (analytics)

**What it does:** Activity history and training analytics. Implemented in `src/client/routes/project/Progress/`.

**UI / UX:**
- Date-range selector (7/14/30/90 days, all-time); stats cards; three tabs: **Activity** (log grouped by day, edit date / duplicate / delete / bulk-delete with undo, manual add for missed sets), **Charts** (volume over time, muscle-group breakdown), **Summary** (daily volume cards)
- **Recovery score** (0–100, Low/Adequate/High): recent training load vs ~30-day baseline

**APIs:**
| Endpoint | What it does |
|---|---|
| `activity-logs/get-activity` | enriched log (exercise name/image/muscle, plan name); max 200 items |
| `activity-logs/get-summary` | volume aggregated by day/week/month |
| `activity-logs/edit-activity` / `duplicate-activity` / `delete-activity` / `bulk-delete-activity` | corrections; bulk delete capped at 100 |
| `activity-logs/get-recovery-score` | load-vs-baseline score (`handlers/getRecoveryScore.ts`) |

**Data:** reads/writes `setLogs`.

### `/share/:token` — Shared Plan (public)

**What it does:** Public, unauthenticated preview of a shared plan; lets the visitor add it to their own account. Implemented in `src/client/routes/project/SharedPlan/`.

**UI / UX:** plan preview + "Shared by {owner}"; logged-out visitors get a login modal and the add-intent is remembered through login; the plan snapshot is static (no live link to the original).

**APIs:** `training-plans/get-shared` (public — decodes the base64url token, returns plan export + owner display name, `handlers/getSharedPlan.ts`); `training-plans/create-from-text` with `autoResolveUnmatched: true` (unmatched exercises auto-create custom definitions in the recipient's library, creationSource='share').

### `/agent` — Coach (AI agent, fullscreen)

**What it does:** Chat with **Coach**, the app's AI training assistant, built on the template agent engine (conversations, streaming, traces). Project-specific parts: `src/apis/template/agent/runtime.ts` (system prompt + handler path, project-overridden) and `src/server/project/training-coach/`.

**Persona & rules (from the system prompt):** warm, encouraging strength-training coach; must use tools instead of guessing; must confirm destructive changes via `ask_user`; no medical advice; only this user's data.

**Tools:** `ask_user` (human-in-the-loop multiple choice) plus 17 auto-exposed API tools (`apiMeta` opt-ins): read plans/exercises/library/week-progress/activity/summaries/exercise-history/recovery-score; mutate plans (create/update/delete/set-active), plan exercises (add/update/delete), and weekly sets (`weekly-progress/update-sets`: add / remove / complete-all). Runs as `isAdmin: false`, userId-scoped.

**Models:** Claude Code adapter (haiku/sonnet/opus) and Codex adapter (gpt-5.x) via the local RPC daemon — turns execute on the developer machine, not Vercel.

## Shared Features

- **`features/project/plan-data`** — the local-first engine for plan exercises + weekly skip flags: Zustand store in localStorage, debounced sync (`plan-data/sync`), staleness check (`plan-data/version`, every mutating handler "touches" the plan), conflict surfacing. Used by Home, ManagePlan, ActiveWorkout.
- **`features/project/workout`** — current week, active plan id, view prefs, and the persisted live-session store (timers, superset, warmup). Used by Home, ActiveWorkout, and the top-nav status bar (`src/client/components/project/ActiveWorkoutStatusBar.tsx`).
- **`features/project/plan-workouts`** — React Query hooks for workout templates (optimistic CRUD). Used by Home, ManagePlan, ActiveWorkout.
- **Weekly exercise notes** — per exercise-definition, per week (`weekly-progress/get-exercise-notes` / `update-exercise-note`); current week's note plus history of previous weeks; empty content deletes.

## DB Schema Summary

| Collection | Document fields | Owned by |
|---|---|---|
| `trainingPlans` | name, durationWeeks (1–52), isActive (one per user), creationSource ('manual'\|'ai'\|'import'\|'share'\|'duplicate'), lastDataSyncedAt, timestamps | per-user |
| `exerciseDefinitions` | name, imageUrl, primaryMuscle, secondaryMuscles[], type, isBodyweight, isStatic, isSystem, userId (custom only), timestamps | global (system) + per-user (custom) |
| `planExercises` | planId, exerciseDefId, sets, reps, weight (kg), durationSeconds, comments, order, overrides? (sparse per-plan customization of the definition) | plan-scoped |
| `planWorkouts` | userId, planId, name, items[{planExerciseId, order, sets?}], order | per-user |
| `setLogs` | userId, planId, planExerciseId, weekNumber, setNumber, completedAt, workoutId? — **source of truth for progress**, one doc per completed set | per-user |
| `exerciseProgress` | weeklyProgressId, planExerciseId, isSkipped? (live), setsCompleted/isDone (legacy, ignored) | plan+week scoped |
| `weeklyProgress` | planId, weekNumber (thin per-week anchor row) | plan-scoped |
| `weeklyNotes` | userId, planId, exerciseDefId, weekNumber, content | per-user |

Cascades: delete plan → everything under it; delete plan exercise → its setLogs + exerciseProgress; delete custom exercise definition → **blocked** while referenced by any plan.

## Background Work & Integrations

- **Coach agent turns** run via the template RPC-over-MongoDB daemon on the local machine (`yarn daemon`); the handler is `src/server/project/training-coach/handler.ts`. No project cron jobs or scheduled work.
- **AI calls** (all via `AIModelAdapter`, cost returned to the UI): plan generation from text (`training-plans/generate-from-text`), warmup generation (`workout-warmup/generate`), and a generic `chat/send` endpoint (legacy, default gemini-2.5-flash).
- **Vercel Blob** (`BLOB_READ_WRITE_TOKEN`): custom-exercise images and per-plan override images.
- **MCP/SDK access**: agent skills and scripts manage training data through the same APIs (`@training-app/sdk`, `mcp__training-app__*` tools) — this is why the plan-version staleness check matters: external writes show up as sync conflicts in the PWA.

## Unrouted / legacy code

`src/client/routes/project/Dashboard/`, `AIChat/`, and `ThemeSettings/` exist but are not registered in `src/client/routes/index.project.ts` — leftover from earlier iterations, not reachable in the app.
